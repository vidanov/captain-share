    One library. Many independent projects.

    A local tool for sharing skills, agents, prompts, and instructions across repositories. Each library owns its originals and keeps its own access rights. Each project chooses what to use and contribute.

    Start here

    1. Set up once. Pick the agents you use, add your team library, and take the starter set if it has one.
    2. Get what you need. Library shows what is new since you last looked, what you have, and the rest. Get installs everywhere for you, or only in this project.
    3. Share what works. Share lists skills you made or edited. Sharing copies them into the library, commits with your note, and pushes. Paste the line it gives you in chat; teammates run captain-share get NAME.
    4. Where installed shows the full grid of projects, folders and your user, plus Projects, Local files and Archive.

    What “current folder” means

    The exact directory where you start the CLI is the target. The web interface stays attached to that directory for its whole session. 

    cd /path/to/project
captain-share serve --open

    Choose another target explicitly:

    captain-share --target /path/to/project serve --open

    The folder picker browses the computer running Captain Share. It fills the path field; choosing a folder does not connect, install, or clone anything.

    How sharing works

    Install
    Creates live symbolic links to library originals. Editing an original, or pulling updates into its checkout, updates every project linked to it.
    Share back
    Copies selected local originals into a library checkout. Review and commit those changes before pushing. Deselecting outbound content leaves the library copy in place.
    Tools
    Each installed asset gets one live link per enabled agent that reads its kind, all pointing at the same original. Kiro and Copilot are on by default; light Claude or Codex in a column head to also link skills into .claude/skills/ or .agents/skills/. There is no copying back and forth between tool folders.
    Aliases
    Change the local file or folder name; set them with the CLI (select inbound … --alias NAME). They do not rewrite skill frontmatter or references inside agents.
    Source of truth
    The library holds the maintained original. To move ownership there, share the original back, archive the local copy, then install the library version.

    Archive and restore

    Archiving preserves a local file, directory, or link and disables its managed inbound selection. A shared original remains in its library.

    Restore puts the asset back if its destination is free. Completed restores are grouped under Restore history. Check Installed for the current link status.

    Archives live in the owning folder’s .captain/archive/. Replaced outbound copies are archived in the library. There is no permanent-delete command.

    Supported assets and destinations

    Libraries can store these asset groups under ip/ or directly at their root. Choose the matching layout when connecting.

    Asset group Expected format Project destination
    Skills Folder containing SKILL.md .kiro/skills/ (Kiro), .claude/skills/ (Claude Code), .agents/skills/ (Codex)
    Agents .json files .kiro/agents/
    Prompts .md files .kiro/prompts/
    Steering .md files .kiro/steering/
    Kiro powers Folder with plugin.json or POWER.md Installed user-wide by kiro-cli into ~/.kiro/powers/installed/
    Copilot repository instructions copilot-instructions.md .github/
    Copilot scoped instructions .instructions.md files .github/instructions/
    Copilot prompts .prompt.md files .github/prompts/

    Housekeeping files such as .DS_Store, .gitkeep, and __pycache__ are omitted from discovery and shared copies. Unrelated file types and prompt subfolders are not listed.

    Repository controls

    Switch repository status between the selected library and the current project’s Git root. It shows new, modified, staged, and deleted files, the branch, and ahead/behind counts from the last fetch.

    • Clone: uses existing Git credentials. Choose a new folder under an existing parent. Submodules are not cloned.
    • Pull: requires a clean checkout and accepts fast-forward updates only.
    • Push: sends committed changes to the displayed destination after confirmation. Commit edited files in your Git client first.

    Git operations are explicit. They preserve existing hooks, do not force-push, and do not resolve conflicts or make commits automatically.

    Configuration and access

    Settings are inherited in this order: global defaults, ancestor project folders, then the target folder. A more specific selection wins.

    ~/.captain/sharing.json
    Global defaults.
    .captain/sharing.json
    Portable library choices and selections for a folder.
    .captain/sharing.local.json
    Machine-local checkout paths, kept out of Git.
    .captain/sharing-state.json
    Local installation and copy records.

    Use the CLI for global/folder scopes, imports, and target registration. Each target must be synced explicitly. Connecting a library does not grant repository access or change its permissions.

    Local operation and limits

    The interface runs on 127.0.0.1 with a per-launch access token. It has no analytics, CDN assets, or automatic model calls. Remote Git actions use your existing authentication.

    Previews are checked again before changes are applied. Unowned files, changed copies, occupied restore destinations, and retargeted links produce conflicts.

    Outbound checks flag recognizable credentials and personal paths; review private or customer material yourself before contributing it to a wider library.

    Links are live, not pinned to commits. Agent dependencies must be selected explicitly. File placement does not prove skill activation in an IDE or CLI. Windows is not currently supported.

    CLI, setup, and assistance

    Requires Python 3.9+, Git, and macOS or Linux. The installed tool has no third-party runtime packages and needs no frontend build step. Captain is not a runtime dependency.

    From the source checkout:

    ./bin/captain-share --help
./bin/captain-share --target /path/to/project serve --open

    Install in a virtual environment:

    python3 -m venv .venv
.venv/bin/pip install .
.venv/bin/captain-share --help

    The bundled manage-shared-assets skill guides setup and maintenance. captain-share assist "your request" prepares a handoff; adding --run explicitly starts Kiro CLI with its normal approval behavior.

    When something needs attention

    • Connection expired: open the complete URL printed by the running server.
    • Missing library: check the local checkout path and selected layout.
    • Pull unavailable: commit or stash local changes in your Git client.
    • Authentication failed: verify repository access in your Git client; the web UI does not prompt for credentials.
    • Preview became stale: preview again after the files or configuration change.
    • Missing link: preview and apply to repair it. A replaced or retargeted link needs review. 
    captain-share status
captain-share config
captain-share --help

    When reporting a problem, include the version, operating system, action, and error message. Remove credentials and private paths from shared reports.

    Development and license

    Captain Share contributors maintain this standalone sharing tool. Library content retains its own ownership, permissions, and licensing.

    Source documentation includes README.md, CONTRIBUTING.md, and the configuration, migration, and design guides in docs/. Development requires Node 22+ in addition to Python and Git. 

    make bootstrap
make verify-fast
make verify

    Local and CI checks share the same verification entrypoint and use disposable repositories. A passing installation check does not measure agent performance.
